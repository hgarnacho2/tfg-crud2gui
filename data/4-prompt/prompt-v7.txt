OBJETIVO
Devuelve el modelo de clases Java que debe existir al terminar la última etapa obligatoria, incluyendo los elementos opcionales descritos. Excluye bibliotecas (String, Date, etc.), ejemplos ajenos a la práctica y clases cuyo código completo ya proporciona el enunciado (lanzadores, ejemplos, interfaces de usuario y pruebas).

PRIORIDAD DE LA EVIDENCIA
* Nombres de clases, métodos y constructores: prevalece el código de ejemplo; si contradice el texto, usa el nombre del código y registra CONTRADICCION.
* Requisitos narrativos: prevalecen para tipos y semántica; después cuentan las llamadas, literales y declaraciones de ejemplo.
* La introducción y las salidas de ejemplo solo apoyan. No modeles conceptos mencionados únicamente en la introducción.
* No inventes elementos: cada clase, miembro y relacion debe tener evidencia en un requisito, diagrama o ejemplo, o derivarse de las reglas siguientes.

ALCANCE Y ETAPAS
1. Las etapas son acumulativas. Devuelve un único modelo final; ante cambios, conserva solo la versión de la última etapa obligatoria. No incluyas estados intermedios.
2. Lo opcional solo anade elementos; no altera nombres ni firmas obligatorios. Incluye las clases opcionales con su kind, superclass y relaciones.
3. Marca optional: true solo cuando la única exigencia que justifica ese elemento sea opcional. Una llamada en una parte opcional prueba su firma, pero no la vuelve opcional si también se exige fuera de esa parte. Evalúa cada sobrecarga y miembro por separado.
4. Considera opcional una parte que el texto identifica como "opcional", "parte opcional", "etapa opcional" o "PARTE OPCIONAL". Para cada elemento opcional, marca optional: true y emite tambien su aviso: "OPCIONAL: Clase", "OPCIONAL: Clase.atributo" o "OPCIONAL: Clase.metodo(Tipo, Tipo)". Una clase opcional no hace opcionales automaticamente sus miembros. Una clase nueva que extiende otra debe conservar la herencia aunque sea opcional.
5. Si una capacidad opcional no tiene nombre ni firma, no la inventes; emite solo un aviso OPCIONAL.

CLASE GESTORA
Si el enunciado asigna explícitamente la gestión o coordinación central a una clase, pon su id simple en expectedManagerId. Si no designa ninguna, usa null. Si hay varias candidatas plausibles o no se puede decidir, usa null y registra "AMBIGUO: Gestora: ClaseA, ClaseB; motivo". No deduzcas la gestora por el nombre ni por heurísticas estructurales. Incluye siempre expectedManagerId en la raíz; si no es null, debe coincidir con un id de types. Comprueba que no se omita antes de devolver el JSON.

DERIVACION DE MIEMBROS
* Atributos: modela las características atribuidas a una clase y todo valor que deba conservar entre llamadas para funcionar. No conviertas parámetros, resultados calculados ni temporales en atributos salvo que deban conservarse. Los datos compartidos van en la clase padre y los específicos en la hija. Si el identificador no está fijado, elige uno canónico y avisa "NOMBRE_ATRIBUTO_NO_ESPECIFICADO: Clase.nombreCanonico". Los atributos static llevan STATIC cuando el texto los declara de clase.
* Accesores: si el texto exige consultar y modificar los atributos dentro de un alcance definido (incluidas expresiones como "todos los atributos" o "como en las clases anteriores"), deriva getX y setX para cada atributo cubierto, también para los añadidos posteriormente dentro de ese alcance. No dupliques accesores heredados ni extiendas la regla a clases fuera de alcance. get devuelve el tipo del atributo; set devuelve void y recibe un parámetro con el nombre del atributo. Para colecciones gestionadas por operaciones específicas de añadir/eliminar, set masivo es opcional: inclúyelo solo si se exige o el código final lo invoca.
* Constructores y métodos: registra una firma por cada combinación distinta de nombre y tipos de parámetros evidenciada por llamadas o requisitos. Diferente número de argumentos o tipos puede ser una sobrecarga válida; no la descartes solo por compartir aridad. Elimina una firma anterior únicamente cuando una etapa posterior indique que la reemplaza. Si la evidencia no permite decidir si la firma se reemplazó o coexiste, aplica la prioridad de evidencia y registra CONTRADICCION o AMBIGUO según corresponda. Usa el orden de los argumentos de las llamadas; nombra parámetros como el atributo que inicializan cuando sea evidente.
* Métodos nombrados en el texto: incluye todo método con nombre y paréntesis que pertenezca a una clase modelada, aunque no aparezca en el ejemplo. Deduce parámetros y retorno solo cuando haya evidencia. Si se exige añadir/eliminar elementos de una colección sin nombrar métodos, no inventes firmas: emite "OPERACIONES_LISTA: Clase.atributo(add,remove)" con solo las operaciones exigidas. Para otras capacidades sin nombre, emite NO_ESPECIFICADO. No conviertas efectos de ejecución en requisitos estructurales.
* Tipos: los literales enteros implican int y los decimales double (o float si lo indica el texto), salvo que el requisito especifique otro tipo. Para colecciones, usa ArrayList solo si el texto dice literalmente ArrayList; si dice lista, usa List; si dice conjunto, usa Set. Conserva el tipo del elemento. No uses Object ni tipos unión. Ante una contradicción de tipos, aplica la prioridad de evidencia y avisa CONTRADICCION.
* Retorno: usa el tipo expresamente indicado. Los set, métodos descritos como imprimir/mostrar/listar por pantalla y las acciones añadir/eliminar/buscar cuyo ejemplo solo imprime un mensaje y se invocan como sentencia devuelven void (TypeRef de nombre "void", nunca null). Usa null solo si no puede determinarse.
* Visibilidad: si el texto manda considerar o decidir la visibilidad de atributos (por ejemplo, al hacer abstracta una clase), usa visibility null y avisa NO_ESPECIFICADO; esta regla prevalece sobre las demás. En otros casos, atributos PRIVATE cuando se exige encapsulación o se declaran privados. Clases, constructores y métodos invocados desde otras clases del modelo o desde lanzadores/interfaces son PUBLIC. En los demás casos usa null.
* Modificadores: usa ABSTRACT solo cuando el texto haga abstracta la clase y STATIC solo según las reglas de atributos. hasBody es true para métodos que debe implementar el estudiante y false solo para métodos abstractos. initializedInline es false salvo que se pida inicializar el atributo en su declaración.
* Enumerados: usa kind ENUM; representa cada valor en enumConstants como {"name":"VALOR","javadoc":null}, nunca como cadena.
* Sobrescritura: registra en la hija un método heredado cuando el texto indique que cambia su comportamiento o los ejemplos demuestren contenido propio de la hija. Conserva la firma del padre.

RELACIONES
* Herencia: registra INHERITANCE de hija a padre (via y multiplicity null) y establece superclass en la hija.
* Cada atributo cuyo tipo, o tipo de elemento de una colección, sea una clase del proyecto (incluidos enumerados) genera una relación desde la clase propietaria al tipo, con via igual al atributo. Los tipos de biblioteca no generan relaciones.
* Usa COMPOSITION cuando el texto declare esa semantica. Una seccion que anuncie composicion la aplica a las relaciones concretas que enumere como parte de su implementacion, aunque cada requisito no repita el termino; no la extiendas a otros atributos. Si el destino es un enumerado, usa siempre ASSOCIATION y no avises AMBIGUO. Usa AGGREGATION solo si se declara explicitamente. Para otras referencias de proyecto, usa ASSOCIATION; si la semantica es dudosa, confidence LOW y aviso AMBIGUO.
* confidence: HIGH si el texto declara la semantica, MEDIUM si se deduce de un ejemplo, LOW si es dudosa.
* Multiplicidad en el extremo destino: "1" si el atributo único es obligatorio o se inicializa mediante un parámetro requerido del constructor, aunque exista un setter o cambie después. Un setter indica mutabilidad, no opcionalidad. Usa "0..1" solo si el texto permite explícitamente que la referencia esté ausente al crear el objeto o que se asigne después sin ser obligatoria. Usa "0..*" para colecciones y null si no hay evidencia suficiente.
* No generes DEPENDENCY ni REALIZATION salvo que el texto las describa expresamente. evidence siempre es null.

AVISOS (source.warnings)
Usa una lista de textos breves, de máximo 25 palabras cada uno, con uno de estos prefijos:

* "CONTRADICCION: ..." para evidencia incompatible de nombres, tipos o usos.

* "OPERACIONES_LISTA: Clase.atributo(add,remove)" para operaciones de coleccion exigidas pero sin nombre de metodo.
